2.6 · 三值键检索缺口 C 的解法 · 新增

原理 检索不需要幅度

检索只做排序，从不使用键的模长。所以每个键可以 像本仓库的三值权重一样，存成两个位平面 P（正）与 M（负）：
agree    = (Pq & Pw) | (Mq & Mw)
disagree = (Pq & Mw) | (Mq & Pw)
dot      = popc(agree) − popc(disagree)
  • 每 32 维：4 个 AND、2 个 OR、2 个 popc
  • 每键 D/4 字节，而非 D×2 → 8× 减少
  • 结果按 1/√nnz 归一，使不同稀疏度的行可比

2.8 · 语境语义由环境决定 · 新增 v4.5

一句话

同一个符号，在不同的环境里表达不同的意思。 语境不是句子的附加信息，语境就是语义本身—— 脱离语境，符号只是形状。

2.8.1 问题：系统只看形状，不看环境

审查者在本轮独立审计中复现出的一批失效， 表面上是四个不同的 bug，根因是同一条：

输入系统认为实际语义符号
read the file C:/tmp/a.txt路径 路径/
compare C++/Rustlist_dir {"path":"C++/Rust"} 两个语言的比较/
what is 40 - 14算式 算式-
写一个 10-14 个词的句子calc {"expr":"10-14"} 数量范围-

六行里三行是对的、三行是错的， 而对错无法由符号本身判断—— /、-、执行 在每个正确用例与每个错误用例里 是同一个字符。

这就是 98 个缺陷里最深的根

前 97 个缺陷都是在符号层面打补丁： 「put 藏在 output 里」→ 加词边界； 「 to 藏在 into 里」→ 按长度优先； 「 in 前面是字母」→ 去掉前导空格。 每一次都对，每一次都只对那一个符号。

下一条符号出现时，补丁不认识它。 因为补丁的判据是形状，而形状在换环境后不变、含义却变了。

2.8.2 语境由三条轴确定

① 领域环境

这个 / 出现在文件系统语境， 还是编程语言语境？

C:/tmp → 盘符 + 分隔符 → 路径
C++/Rust → 语言名 + 并列 → 不是路径

判据：斜杠左侧是否是一个合法的卷名或目录段。 C++ 不是卷名，也不是目录段。

② 语言环境

中文的执行与英文的 run 在隐喻上同样脆弱。

执行计划 → 「按计划办事」
执行 Get-Location → 「运行这条命令」

判据：载荷是否为命令形—— 命令是 ASCII 可执行名 + 参数，中文长句不是。

③ 句法环境

这个 - 是运算符还是连接符？

40 - 14 → 减法
10-14 个 → 范围（后面跟量词）

判据：数字对后面是否紧跟量词/单位。 量词把数字对变成名词短语的一部分。

2.8.3 机制：符号只有被语境许可才是证据

唯一规则

一个符号不构成证据，直到语境为它颁发许可。

实现为一个许可函数，而不是一串补丁：

  licensed_as_path(text, span)      → 这个 span 在此语境里读作路径吗
  licensed_as_expression(text, span) → 这个 span 在此语境里读作算式吗
  licensed_as_command(text, span)    → 这个 span 在此语境里读作命令吗

三个函数共享同一副骨架： 取 span、看左邻、看右邻、看所属领域。 新增一种符号时，只需说明它在什么语境下被许可， 而不需要再写一个「藏在谁里面」的特例。

#98shell 载荷须为命令形 这已经是语境判据——只是没有名字，也没有复用到别处

结论

语境层不是新增的一个功能， 是把已经散落在 98 个补丁里的同一条判据提炼出来。

补丁的形状是「这个符号在此处不是那个意思」； 语境层的形状是「这个符号在什么条件下才是那个意思」。 前者随符号数量增长，后者随领域数量增长——而领域只有三个。

31 多词 shell 命令被截断成最后一个词 载荷兜底规则取最后一个空白分隔的 token，对 hostname 正确，对带参数的命令全错：
ipconfig /all → {"cmd":"/all"}（丢了程序名）
netstat -an → {"cmd":"-an"}
ping -n 3 → {"cmd":"3"}（程序名和标志都丢）

32 斜杠标志被误判为路径 修好上面的规则后 ipconfig /all 仍然错： 路径分支把任何 / 当路径分隔符，抓走 /all。
必须把引导短语检查提到路径规则之前—— 「命令里含斜杠」不能被「含斜杠即路径」抢走。 测 6 条多词命令，修前 3 错，只把引导规则提前后 5/5 全对
33 多动作请求被静默错配 语料中零个多动作样本，而系统对这类请求不是失败，是 把两个小句的工具和载荷拆开重组：
read the file X and list the directory Y → list_dir {"path":"X"}
what is 12 * 7 then list the directory Y → list_dir {"path":"12*7"}
first read X then run the command hostname → read_file {"path":"hostname"}
工具取自第二小句、载荷取自第一小句。 每条都是合法 JSON、干净执行、做错事
34 “检测并拒绝”优于“尝试回答” 教模型输出两个工具调用需要不存在的数据和协议改动； 而识别模式两样都不需要。拒绝是可恢复的结果—— 用户立刻知道限制，而不是照着错误输出行动。
与「裸路径默认读」同一原则：宁可给可恢复的结果， 不给自信的错误答案。误判代价：文件名含 and 的合法请求会被误拒， 故第二小句必须含动词或裸命令名才判定为多动作

add 456 and 781 → calc {"expr":"me"}
30% off 279 → calc {"expr":"279"}
根因：真实用户用词，合成语料只有符号。 x/plus/times/percent off 一个都不在语料里。修后 8/8
36 提取与判定用了不同的字符串 修好提取器后 7 x 7 仍错：extract_payload 会先规范化词运算符（得到 7*7），而 looks_like_expression 在原文上跑， 找不到符号就返回 false，于是路由判成目录。
两个环节必须测同一个字符串—— 「提取对了」不代表「判定对了」
37 「含斜杠即路径」三次抢走算式 同一类顺序错误在本文件出现三次：
① ipconfig /all → {"cmd":"/all"}（shell 标志被当路径）
② cmd /c dir → {"cmd":"/c"}
