# 共谋盲点与三种外部检验

## —— 一个单人项目的 29 个变异测试与 136 个缺陷

---

## 摘要

本文报告一个单人、无版本控制、无代码评审的项目的质量保证实践。

起点是一个观察：**同一双手写出的代码与测试，共享同一批盲点**。
测试会通过，不是因为代码正确，而是因为测试只检查了作者想到的东西。

本文提出并实测了三种**外部检验**，每一种都立刻发现了自查发现不了的缺陷：

| 检验 | 换掉了什么 | 立刻发现 |
|---|---|---|
| 换考题 | 合成测试集 → 真实语料 | 域外误执行率 **92%**（自查时为 0%） |
| 换审查者 | 自己 → 不共享上下文的审查 | **8 个**数据破坏级缺陷 |
| 换工具 | cmd 批处理 → PowerShell | 驱动从四轮不过到一次全过 |

此外，本文把**变异测试**形式化为可执行的门禁：当前 **34 个变异，
全部被对应套件抓住**。

**核心主张**：在一个没有同事的项目里，唯一可靠的质量来源是
**主动制造「不同来源」的检验**，而不是更仔细地自查。

---

## 1. 问题：为什么自查不够

一个具体的例子。测试集会报告 `ALL PASS`，看起来一切正常。
但这个 `ALL PASS` 可能来自三种完全不同的情况：

| 情况 | 代码 | 测试 | 输出 |
|---|---|---|---|
| A | 正确 | 覆盖了 | ALL PASS |
| B | 正确 | **什么都没检查** | ALL PASS |
| C | **错误** | **检查了一个恒真条件** | ALL PASS |

**三者输出完全相同。** 而作者的自查只能区分 A 和「不是 A」，
无法区分 B 和 C——因为要区分它们，需要知道测试**没有**检查什么，
而这恰恰是作者的盲点所在。

本文的全部工作都是在回答一个问题：**如何让 B 和 C 暴露出来。**

---

## 2. 变异测试：让「不能失败」变成可检测

### 2.1 原理

对源码施加一个**故意的、错误的**小改动，然后跑对应测试。**测试必须失败。**

| 结果 | 含义 | 应对 |
|---|---|---|
| 测试失败 | 变异被抓住 | 正常 |
| 测试通过，且行为确实变了 | **空洞**：测试没覆盖这个行为 | 补测试 |
| 测试通过，且行为没变 | **无效变异**：瞄错了位置 | 改变异 |

**第二行和第三行的区分至关重要**，而第一版实现没有区分——
两者都打印「passed WITH THE MUTANT IN PLACE」。

### 2.2 第三行的发现方式

给每个变异配一条**探针**：一条答案必然因该变异而改变的请求。
施加变异前后各跑一次，**答案相同即无效变异**。

这个设计抓到两个真实案例：

| 变异 | 为什么无效 |
|---|---|
| 删掉分隔符表项 `over to` | `copy X over to Y` 也含 `to`，删了行为不变 |
| 改 `has_action_word` 的返回 | 测试输入 `alpha_and_beta.txt` 含 `_and_` 而非 ` and `，根本走不到 |

**第二个案例的教训**：第一次看到「变异未被抓住」时，
吾的第一反应是「测试有洞」。**错了。** 是变异瞄错了地方。
这个方向判断错了会浪费一整轮去找一个不需要存在的测试。
### 2.3 结构限制：变异台不能重建自身

变异循环要重新编译，而变异台就是被编译的那个二进制。Windows 锁定运行中的映像，
所以链接失败（`LNK1104`），而**八个变异全被报成「不编译」**——
一句真话，说的是错的事。

两次尝试都失败：

1. 直接重编 → 锁住
2. 复制自身再跑 → `std::system` **阻塞**，父进程仍是活的映像

**结论：这是结构限制，不是能绕过的实现问题。** 故拆成两段：
`am-mutate --apply/--restore` 只改字节，驱动脚本在**外面**循环——外面没有锁。

**承认结构限制，好过一个半灵的取巧。**

### 2.4 当前结果

34 个变异，覆盖 22 个套件，**全部被抓住**。

并且这个覆盖是**强制的**：若新增一个测试套件而没有对应变异，
`am-source` 会失败。这把「应当做变异测试」从建议变成了门禁。

## 3. 三种外部检验

### 3.1 换考题：合成数据 → 真实语料

合成测试集报告 100% 留出集准确率。换成真实语料后：

| 语料 | 域外误执行率（改进前） | 改进后 |
|---|---|---|
| CLINC150（英文） | **92.0%** | **1.3%** |
| alpaca_zh（中文） | 6.2% | **0.3%** |

**92% 意味着：不属支持范围的请求，有九成被真的执行了。**
这个数字在合成测试集上永远是 0%，因为合成测试集的「域外」样本也是按同样方式造的。

**这是本文最贵的单条发现。** 它不是「有个 bug」，
而是「测试的设计使那类 bug 不可能被看见」。

### 3.2 换审查者：自己 → 不共享上下文

请一位**没有本项目上下文**的审查者对代码做独立审计，
在 9 轮自查之后，又发现 **8 个缺陷，其中 4 个是数据破坏级的**：

| 缺陷 | 后果 |
|---|---|
| `write_file` 用 `CREATE_ALWAYS` | **静默覆盖已有文件**（实测把文件替换成 5 字节） |
| `run_shell` 永远返回退出码 0 | 失败被报告为成功 |
| `run_shell` 输出永远为空 | 结果不可见 |
| 两个矛盾的 `-4` 拒答文案 | 同一个码两种说法 |

**这些都不是难发现的 bug**，而是**作者的注意力恰好不在那里**。

**一个反例也值得记录**：该审查者有一条结论是错的（声称某三个输出逐字节相同），
实测并不相同。**外部结论本身也需要复现。**

### 3.3 换工具：cmd → PowerShell

变异测试的驱动脚本最初用 cmd 批处理写，以**四种不同方式**失败：

| 失败 | 原因 |
|---|---|
| 运行中编辑执行新旧混合内容 | cmd **逐行读取**批处理文件 |
| `:mut` 落穿进 verdict 段 | 缺 `goto :eof` |
| `for /f` 抓不到探针答案 | 子过程里的变量展开 |
| 计数器在加而判定行不打印 | 嵌套 `if(...)` 里 `errorlevel` 传播丢失 |

**没有一个是关于变异测试的，全都是关于 cmd 的。**

改写为 PowerShell（真循环、真变量、真字符串比较，十几行）：
**一次达成 34 caught / 0 holes**。

**这是本文第三条外部检验：当工具开始对抗时，换掉它，而不是再加一层变通。**

## 4. 从 136 个缺陷提炼的判据

按出现次数排序，前五类覆盖绝大多数：

| 判据 | 出现 | 一句话 |
|---|---|---|
| 装置失效 | 20 | 不能失败的机制和通过了的机制，在输出上无法区分 |
| 手工清单 | 17 | 两份需要手工保持一致的清单，必然分叉 |
| 不可达 | 15 | 不能改变行为的代码，指向的是不能起作用的代码 |
| 子串匹配 | 12 | 按共享子串判断，无法分辨两条不同的消息 |
| 早退 | 10 | 写在早退之后的代码是死代码 |

这份清单被写成 `CRITERIA.md`，并由 `am-source` 检查它存在且完整——
因为**清单本身也是需要保持一致的东西**，所以它也被纳入门禁。

---

## 5. 局限

1. **n = 1。** 本文是一个项目、一个人、一个领域。判据的普适性未验证。

2. **没有版本控制。** 全部工作在一个工作树里，无法做「回滚后重测」这类实验。
   这是一个真实的工程缺陷，不是设计选择。

3. **变异测试的覆盖是自证的。** 变异表由作者写，所以它只能证明
   「作者想到的那些行为」被测试覆盖了，不能证明「所有行为」。

4. **外部审查只有一次。** 8 个缺陷来自一次审计，之后没有第二次。
   无法判断这类审计的**持续**收益。

```
cd canticle

.\build\canticle.exe criteria           # 8 条判据全文
.\build\canticle.exe am-source          # 含「每套件至少一条变异」检查
```

## 7. 结论

单人项目的质量不能靠更仔细的自查，因为自查的盲点就是问题本身。

三种外部检验各有分工：

- **换考题**发现「测试设计使某类 bug 不可见」
- **换审查者**发现「注意力不在那里」的缺陷
- **换工具**发现「用错层次」的浪费

而**变异测试**是把第三种自查变成可执行门禁的手段：
它不问你写了什么测试，只问**如果你写错了，测试会不会响**。

**最重要的单条结论**：当一件事反复修不好时，
先问「是不是层次/工具选错了」，而不是继续加变通。
本文在这一条上浪费了四轮，而换工具后一次通过。
