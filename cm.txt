阶段 2 第一刀：命令词表闸门补上模板许可，堵住编造命令名

发现（不是设计出来的，是测出来的）：
  run the command zzznotacommand   -> 执行了
  run the command foobarbaz        -> 执行了
  execute qwertyuiop               -> 执行了

根因：载荷闸门是 if (!confident && tokens > 6 && !licensed_as_command_strong(pay))
tokens > 6 用来代表「这像一句散文，最后一个词是散落的」，
而 run the command X 只有 1 个 token，于是词表检查整个被跳过。

判据用错了：许可载荷为命令的不是句子长度，是模板。
run the command X 已经声明 X 是程序，此时词表必须同意——
（这正是「组合」与「编造」的分界。）

修法：
  context::explicit_command_template(text)  新增，识别明确的命令模板
  载荷闸门分两条路：
    明确模板 -> 必须通过词表
    模糊前缀（run/call/launch/start）-> 维持长度启发式
  模糊前缀故意不进模板列表：call hostname 是命令，start the meeting notes 不是，
  只有词表能分开这两者。

诚实记录一条没修好的：
  run the command dir C:/tmp  仍然路由到 list_dir
  原因不是排序，是表示层——24 个候选全是 list_dir 行，
  字符三元组分不清 dir 这个程序与 dir 这个目录名。
  重选代码保留（它修好了 run the command dir C: 这类有候选的情况），
  并在注释里写明它不解决硬情况。
